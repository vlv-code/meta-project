Миграции схем делать явными и версионированными. Повторный запуск после успешной миграции не должен повторно изменять данные.

Приёмка: сбой посередине операции оставляет диагностируемое состояние, из которого можно восстановиться без потери пользовательских правок.

5. Проверять совместимость и фиксировать результат обновления

Обновление общих компонентов проверять относительно всех действующих установок, даже если оно запущено из одной среды.

Проверки разделить на:
- Целостность обвязки, схем, ссылок и границ.
- Совместимость компонентов и установок.
- Прикладные проверки рабочего проекта.
- Нативную проверку загрузки в харнессе.
Команды приложения брать из паспорта и стека проекта. Отсутствие выполненных тестов нельзя представлять как успешный прогон.

Для применения формировать update-отчёт через общий механизм отчётов:
- Версии до и после.
- Источник обновления.
- Затронутые компоненты и установки.
- Выполненные миграции.
- Сохранённые адаптации и конфликты.
- Результаты проверок.
- Оставшиеся ручные действия.
Read-only проверка файлов отчётов не создаёт.

Разрешения на изменение защищённых файлов проверять через общий механизм из предыдущего плана. Новая версия проверяющего кода не должна сама подтверждать допустимость собственной установки.

Режим анализа — read-only. Учесть, что существующий scan умеет изменять знания: для диагностики использовать его чистые проверки, а не запускать весь изменяющий сценарий.

3. Заменить механические признаки проблем анализом свидетельств

Использовать существующие данные: задачи, наблюдения, отчёты, проверки, историю изменений и телеметрию с подтверждённой идентичностью.

Исправить текущие эвристики:
- Три последовательные правки файла — только сигнал для изучения. Это может быть нормальный TDD.
- Тридцать дней без вызова роли не доказывают её ненужность.
- Частые блокировки гейта могут означать корректную защиту.
- Частые вызовы ground могут быть следствием смены сессий.
- Git-автор не определяет проектную роль.
- Отсутствие телеметрии означает недостаток данных.
Окно анализа выбирать по задаче: период, набор завершённых задач или конкретная установка. Жёсткие «последние 15 коммитов» оставить возможным коротким обзором.

Приёмка: обычная итеративная разработка не превращается автоматически в диагноз «агент зациклился».

4. Формировать проверяемые предложения

Для каждого предложения фиксировать:
Наблюдаемая проблема:
Свидетельства и ограничения данных:
Предполагаемая причина:
Предлагаемое изменение и его область:
Ожидаемый эффект:
Способ проверки:
Сохраняемые ограничения:
Способ отмены:
Исполнитель:
Разделять установленный факт и гипотезу. Например, «пять передач задачи между ролями» — факт; «диспетчер плохо распределяет задачи» — гипотеза, которую ещё нужно проверить.

Выбирать небольшой набор изменений с наибольшей ожидаемой пользой. Отсутствие обоснованных предложений считать нормальным результатом.

5. Добавить калибровку инструкций и стоимости контекста

Проверять:
- Дубли правил между паспортом, скиллами и системными промптами.
- Противоречия между согласованным сценарием и инструкциями.
- Процедуры, которые загружаются постоянно, хотя нужны редко.
- Правила без понятного влияния на поведение.
- Устаревшие временные обходы.
- Избыточные обязательные отчёты и подтверждения.
Лимит North Stars применять к итоговому активному набору, а не разрешать добавлять по три при каждом запуске.

При превышении компактного целевого набора предлагать консолидацию и перенос тактических деталей в скиллы или знания. Уже принятые ограничения сохранять; удаление ради достижения числа недопустимо.

Для нового правила указывать ситуацию применения и ожидаемое изменение поведения. Предложение «добавим ещё инструкцию» должно иметь проверяемое основание.

6. Применять изменения через соответствующие механизмы

tune подготавливает согласованный набор изменений:
- Роли и обязанности — через manage.
- Отключение bindings и архивирование — через decommission.
- Обновление framework — через update.
- Локальные инструкции — через общий механизм сохранения адаптаций.
- Изменения границ — через действующую политику разрешений.
Соблюдать ранее предоставленные полномочия. Повторное согласование уже разрешённых действий не требуется. Изменение целей, ослабление защиты или расширение полномочий выносить как отдельное решение.

Перед запросом нового разрешения подготовить конкретный diff и доступные проверки.

Редко используемую роль оценивать по её назначению и необходимости. Например, независимая проверка может оставаться обязательной даже при небольшом числе вызовов.

7. Добавить проверку эффекта после калибровки

Прохождение тестов подтверждает допустимость изменения, но ещё не доказывает его полезность.

Для применённого изменения сохранять:
- Исходное наблюдение.
- Ожидаемый результат.
- Условие повторной оценки.
- Фактически полученный результат.
- Существенные изменения условий за время наблюдения.
Проверять эффект на следующих сопоставимых задачах или при следующем вызове tune. Фоновое наблюдение для этого не требуется.

Различать результаты:
- Изменение применено, эффект ещё не проверен.
- Польза подтверждена наблюдениями.
- Эффект не обнаружен.
- Обнаружена регрессия.
Если одновременно изменились версия framework, харнесс и тип задач, не приписывать результат одной настройке без основания.

Отмена должна восстанавливать только соответствующее изменение, сохраняя последующую работу пользователя.

8. Обеспечить повторяемость и сохранение локальных решений

При одинаковых входных данных повторный запуск не должен:
- Добавлять новые правила ради самого запуска.
- Повторять уже отклонённые предложения без новых оснований.
- Создавать одинаковые наблюдения.
- Перестраивать подходящую команду.
- Записывать файлы в режиме анализа.
Принятые и отклонённые предложения сохранять с основанием и областью действия.

Локальная калибровка не меняет номер upstream-релиза framework. Она должна учитываться как адаптация установленного экземпляра и сохраняться последующим update.

9. Реализация и отчётность

Основные файлы:
- skills/tune-meta-project/SKILL.md и его локальная копия.
- Небольшой stdlib-сборщик фактов, если существующих утилит недостаточно.
- Шаблон tune-отчёта и поддержка в общем механизме отчётов.
- Тесты диагностики, применения и повторной оценки.
Механический сбор данных и проверки выполнять кодом. Объяснение причин и предложения оставлять агенту.

Отчёт должен различать завершение анализа, применение изменения и подтверждение эффекта. Успешно записанный отчёт не означает успешную оптимизацию.
