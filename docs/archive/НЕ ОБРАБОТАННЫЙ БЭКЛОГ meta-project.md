6. Оценить пилот.
Сравнить результаты в одинаковых условиях. Учитывать дополнительные чтения и задержки, а не только размер SKILL.md. Смысл инструкций в этом изменении сохранять.

Да, это стоит встроить в планирование — как выбор способа выполнения каждой подзадачи. Для Meta-Project схема хорошо подходит.



Но экономия денег и экономия токенов различаются: дешёвый субагент может снизить стоимость, даже увеличив общее число токенов. Считать нужно всю цепочку: подготовка → выполнение → проверка → переделки.



Я бы использовал такую маршрутизацию:

Работа	Исполнитель

Хэши, синхронизация, поиск битых ссылок, развёртывание шаблонов	Скрипт

Однотипные правки примеров, небольшой патч по точной спецификации, черновик теста для известного воспроизведения	Дешёвый субагент

Локальная реализация с понятным контрактом	Обычный исполнитель

Архитектура, миграции, границы полномочий, неоднозначные дефекты	Сильная модель и предусмотренная независимая проверка





Роль и модель нужно разделить. Проектная роль сохраняет ответственность за результат. Временный исполнитель помогает ей с ограниченной подзадачей; ему не нужны отдельный постоянный паспорт, кабинет и собственная история команды.

Для делегирования важнее определённость задачи, чем её размер. Правка одной строки в политике безопасности может требовать сильной модели. Десяток одинаковых изменений по утверждённому образцу хорошо подходит дешёвому исполнителю.



Чтобы схема действительно экономила:

\- Передавать компактный пакет контекста: цель, необходимые ограничения, конкретные файлы и ссылки, ожидаемый результат и проверки. Полная переписка каждому исполнителю быстро съест экономию.

\- Группировать однородные мелочи. Один исполнитель на пакет связанных правок обычно разумнее отдельного агента на каждую строку.

\- Получать короткий результат: изменённые файлы, выполненные проверки, оставшиеся вопросы. Основная роль проверяет артефакты.

\- Возвращать неопределённые задачи родителю. При обнаружении нового контракта, расширении области или недостатке данных исполнитель сообщает об этом; обычный цикл TDD сам по себе не означает необходимость эскалации.

\- Сохранять требования проверки. Делегирование не отменяет независимый Guardian, если он предусмотрен сценарием.

С предложением пользователю тоже согласен. В режиме controlled можно показывать один план делегирования на пакет работ. После согласования допустимых типов задач, моделей и бюджета повторные разрешения на каждую мелочь уже не нужны. Это естественно ложится в существующий delegation\_level.



При этом харнесс должен действительно поддерживать выбор модели. Если он запускает всех субагентов на одной модели, само разделение работы ещё не доказывает экономию.



Для сокращения именно токенов я бы одновременно использовал короткие выводы проверок, выборочное чтение файлов, CLI вместо чтения реализаций скриптов и запланированную ленивую загрузку ресурсов.



Начать стоит с одного пилота: пакет однотипных некритичных правок отдать дешёвому исполнителю, оставить приёмку основной роли и сравнить полную стоимость, время и число переделок. tune затем сможет корректировать маршрутизацию по этим наблюдениям.





Ещё можно сократить повторное чтение, повторное планирование и разбор одних и тех же ошибок. Для Meta-Project я бы рассмотрел шесть вещей.

1\. Разные маршруты выполнения задач.

&#x20;  Небольшая правка примера и изменение механизма восстановления требуют разного объёма подготовки.

&#x20;  Режим	Когда использовать

&#x20;  Короткий	Понятная локальная задача: действие → нужная проверка → результат

&#x20;  Обычный	Несколько связанных изменений с известными контрактами

&#x20;  Расширенный	Миграции, неоднозначные дефекты, архитектура, защищённые компоненты

&#x20;  

&#x20;  

&#x20;  Режим выбирается по последствиям и неопределённости. Обязательные проверки согласованного сценария сохраняются.

2\. Кеш проверенных фактов.

&#x20;  Агенту полезно помнить: этот файл уже изучен, его содержимое не изменилось; этот контракт уже проверен данной версией инструмента.

&#x20;  Ключ кеша: входные данные + версия проверяющего кода + параметры. Одного SHA коммита недостаточно из-за незакоммиченных изменений.

&#x20;  Начать можно с чистых операций: разбора реестра, манифеста, ссылок и зависимостей. В read-only режиме кеш держать в памяти или читать существующий, без записей.

3\. Компактный checkpoint задачи для передачи между сессиями.

&#x20;  Сохранять на значимых этапах:

&#x20;  Цель и критерий завершения

&#x20;  Принятые решения и ограничения

&#x20;  Что сделано и чем проверено

&#x20;  Затронутые файлы

&#x20;  Оставшиеся вопросы

&#x20;  Следующий шаг

&#x20;  Ссылки на доказательства

&#x20;  Тогда ground сможет восстановить работу из небольшого пакета. Это особенно полезно при переходе между харнессами. Checkpoint должен проверяться на актуальность относительно рабочего дерева и нового запроса пользователя.

4\. Подача изменений с последнего чтения.

&#x20;  После правки агент получает короткую сводку:

&#x20;  Изменён валидатор идентичности. Затронуты инспектор и intake отчётов. Проверить соответствующие контракты и тесты.

&#x20;  

&#x20;  Это уменьшает повторное чтение всего проекта. Начать можно с явных связей из архитектуры и манифеста, постепенно уточняя их по фактическим зависимостям.

5\. Диагностика, которую легко использовать.

&#x20;  Утилиты могут возвращать стабильный код ошибки, путь, ожидаемое и фактическое состояние, допустимый следующий шаг.

&#x20;  Например:

&#x20;  STALE\_INPUT

&#x20;  Файл: .agents/meta-project.json

&#x20;  Причина: изменён после обследования

&#x20;  Следующий шаг: повторно проверить изменившиеся входы

&#x20;  Агент тратит меньше контекста на догадки и повторные команды. Рекомендация утилиты при этом сохраняет действующие ограничения полномочий.

6\. Учёт стоимости в tune.

&#x20;  Оценивать стоимость принятого результата: подготовку, исполнителей, проверку и переделки. Полезно видеть:

&#x20;  - какие файлы читаются повторно;

&#x20;  - где разрастается входной контекст;

&#x20;  - какие передачи задач оказываются лишними;

&#x20;  - какие дешёвые исполнители требуют дорогих исправлений;

&#x20;  - какие настройки действительно помогают.

&#x20;  Если харнесс не предоставляет токены и стоимость, учитывать доступные показатели отдельно: объём прочитанного текста, обращения к инструментам и время. Не переводить их в выдуманную денежную экономию.

Для этого репо особенно интересны checkpoint задачи и короткий маршрут выполнения: они напрямую поддерживают переносимость и сохранение замысла. А выборочное сокращение тестов сейчас даст меньше пользы: на последнем проверенном срезе полный прогон 197 тестов занял около шести секунд. Гораздо перспективнее измерить, сколько агент тратит на чтение, обсуждение и повторное восстановление контекста.
